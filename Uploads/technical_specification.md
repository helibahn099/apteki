# Техническое задание: сервис поиска лекарств

## 1. Цель проекта

Разработать мобильное приложение для поиска лекарственных препаратов в ближайших аптеках и серверную часть, которая будет управлять поиском, оплатами, взаимодействием с аптеками и обработкой результатов.

Основные технологии:

- Мобильное приложение: Flutter (Dart).
- Backend: Rust.
- OCR: PaddleOCR + Google ML Kit Text.
- Карты: flutter_map + OpenStreetMap.
- Маршрутизация: OSRM / Valhalla.
- Внешние карты: map_launcher.

Архитектура должна быть модульной, чтобы в будущем можно было подключать новые аптечные сети, платёжные системы, ИИ-агентов и службы доставки без переписывания основной системы.

## 2. Мобильное приложение (Flutter)

### 2.1. Авторизация

Реализовать регистрацию и вход по номеру телефона.

Порядок работы:
1. Пользователь вводит номер телефона.
2. Выбирает доступный канал получения кода.
3. Получает одноразовый код.
4. Вводит код и авторизуется.

Предусмотреть безопасное хранение сессии, выход из аккаунта и восстановление доступа.

### 2.2. Создание поискового запроса

Пользователь должен иметь возможность:
- Добавлять несколько препаратов.
- Указывать название.
- Указывать количество.
- Указывать дозировку и форму выпуска.
- Удалять и редактировать препараты.
- Сохранять предыдущие запросы.
- Создавать новый поиск на основании старого.

Добавить сканирование рецептов и упаковок через камеру.

OCR должен работать локально на устройстве. Фотографии рецептов не должны отправляться на сервер или сохраняться приложением.

После распознавания пользователь должен иметь возможность проверить и исправить результат до отправки запроса.

### 2.3. Выбор типа поиска

Реализовать два варианта:

**Базовый поиск:**
- Поиск по указанным названиям.
- Проверка аптек через подключённые системы и сотрудников.
- Отображение полных и частичных совпадений.

**Расширенный поиск:**
- Все возможности базового поиска.
- Анализ действующих веществ.
- Поиск по международным непатентованным наименованиям.
- Поиск возможных аналогов.
- Анализ информации из интернета.
- Уточняющие вопросы пользователю через ИИ-агента.
- Дополнительный сбор информации с сайтов аптек.

ИИ не должен самостоятельно назначать лечение или представлять возможные аналоги как гарантированно взаимозаменяемые препараты.

### 2.4. Геолокация

Реализовать:
- Получение текущих координат пользователя.
- Запрос разрешения на использование геолокации.
- Обработку отказа в предоставлении разрешения.
- Возможность ручного указания местоположения.

Поиск аптек должен расширяться постепенно от текущего местоположения пользователя.

### 2.5. Оплата

Реализовать экран оплаты с QR-кодом.

Требования:
- Валюта: кыргызский сом.
- Поддержка истечения срока действия QR-кода.
- Получение подтверждения платежа от сервера.
- Защита от повторной оплаты одного заказа.
- Отображение статусов оплаты.
- Сервисное уведомление после успешной оплаты.

Платёжная система должна подключаться через отдельный модуль, чтобы её можно было заменить без изменения основной логики приложения.

### 2.6. Результаты поиска

Отображать результаты в виде списка чатов с аптеками.

Для каждой аптеки показывать:
- Название.
- Адрес.
- Расстояние.
- Наличие препаратов.
- Недостающее количество.
- Цены.
- Общую стоимость доступного набора.
- Время последнего подтверждения наличия.

Полные совпадения должны отображаться выше частичных.

Внутри чата реализовать:
- Переписку с аптекой.
- Кнопку звонка.
- Контактную информацию.
- Закреплённую карточку аптеки с адресом.
- Кнопку построения маршрута.

Срок активного чата — 48 часов. После этого чат становится доступен только для чтения и перемещается в архив.

## 3. Серверная часть (Rust)

Backend должен отвечать за всю основную бизнес-логику приложения.

Рекомендуется использовать модульную архитектуру. Для первой версии достаточно модульного монолита с возможностью дальнейшего разделения на отдельные сервисы.

Основные модули:

| Модуль | Назначение |
|---|---|
| Auth | Авторизация и управление пользователями |
| Users | Профили и история поисков |
| Search | Создание и выполнение поисковых запросов |
| Medication | Каталог и сопоставление препаратов |
| Pharmacy | Аптеки и их торговые точки |
| Integrations | Подключение 1С и внешних источников |
| Payments | Обработка платежей |
| Chat | Переписка с аптеками |
| AI | Взаимодействие с ИИ-агентами |
| Geo | Геолокация и поиск ближайших аптек |
| Notifications | Уведомления пользователей и аптек |
| Logging | Системные логи и диагностика |

Модули должны иметь чёткие границы ответственности и взаимодействовать через определённые интерфейсы.

### 3.1. Поисковый движок

Реализовать централизованный механизм поиска.

Он должен:
1. Получать поисковый запрос.
2. Определять тип поиска.
3. Получать список подходящих аптек по географическому положению.
4. Выполнять предварительную проверку.
5. После оплаты запускать полноценный поиск.
6. Отправлять запросы в аптечные системы.
7. Получать ответы сотрудников.
8. Сопоставлять найденные препараты с запросом пользователя.
9. Формировать результаты.
10. Передавать их мобильному приложению.

Предусмотреть постепенное увеличение радиуса поиска.

Установить ограничение: повторный запрос к одной аптеке не должен отправляться чаще одного раза в минуту.

Все параметры поиска должны настраиваться через конфигурацию, а не быть жёстко прописаны в коде.

### 3.2. Сопоставление препаратов

Разработать отдельный механизм сравнения препаратов.

Он должен учитывать:
- Название.
- Действующее вещество.
- Дозировку.
- Концентрацию.
- Форму выпуска.
- Производителя.
- Количество.

Результат сопоставления должен иметь один из статусов:
- Полное совпадение.
- Частичное совпадение.
- Несовпадение.

Алгоритм сопоставления должен быть отделён от ИИ-агента, чтобы базовый поиск мог работать самостоятельно.

### 3.3. Работа с результатами

Система не должна вести постоянную базу аптечных остатков.

Однако необходимо сохранять временный снимок результатов каждого поискового запроса, чтобы:
- Показывать результаты пользователю.
- Рассчитывать стоимость.
- Поддерживать работу чатов.
- Сохранять историю поиска.
- Перемещать чаты в архив через 48 часов.

Такие данные должны относиться к конкретному поиску, а не использоваться как глобальная информация о текущих остатках аптек.

## 4. Интеграции с аптеками и 1С

Разработать универсальный интерфейс подключения аптек.

Нельзя привязывать основную бизнес-логику к конкретной конфигурации 1С.

Для каждой аптечной сети может потребоваться собственный адаптер интеграции.

Основные задачи:
- Получение каталога товаров.
- Получение остатков.
- Получение цен.
- Идентификация торговых точек.
- Отправка запросов на подтверждение наличия.
- Получение ответов сотрудников.

Для аптек без 1С предусмотреть отдельный механизм ручного подтверждения.

Сотрудник аптеки должен иметь возможность ответить:
- Есть полностью.
- Есть частично.
- Нет в наличии.

Также необходимо предусмотреть передачу количества и цены по каждой доступной позиции, чтобы приложение могло корректно формировать результаты.

**Важно:** интерфейс, через который сотрудник аптеки будет отвечать на запросы, пока не определён. Необходимо предусмотреть возможность реализации через веб-панель или отдельный интерфейс для сотрудников.

## 5. Чаты и уведомления

Реализовать серверную систему сообщений.

Требования:
- Привязка каждого чата к поисковому запросу и аптеке.
- Хранение истории сообщений.
- Получение новых сообщений без необходимости перезапускать приложение.
- Уведомления о новых сообщениях.
- Автоматическое закрытие возможности отправки сообщений через 48 часов.
- Перевод чата в архив.

Номер телефона пользователя не должен передаваться аптеке автоматически.

## 6. Платёжная система

Реализовать независимый платежный модуль.

Предусмотреть следующие статусы заказа:
- Создан.
- Ожидает оплаты.
- Оплачен.
- Поиск выполняется.
- Поиск завершён.
- Ошибка обработки.

Подтверждение оплаты должно поступать от платёжного провайдера на сервер.

Повторное получение одного и того же уведомления об оплате не должно приводить к повторному запуску поиска или повторному начислению оплаты.

До выбора банка реализовать тестовый платёжный провайдер (Mock Payment Provider), позволяющий проверять всю платёжную логику без настоящих денежных операций.

## 7. ИИ-интеграция

ИИ-агент должен подключаться через отдельный интерфейс.

Это позволит в будущем менять используемую модель или поставщика без переписывания поискового движка.

Необходимо предусмотреть:
- Передачу списка препаратов.
- Получение уточняющих вопросов.
- Анализ действующих веществ.
- Поиск возможных аналогов.
- Получение кратких объяснений.
- Поиск информации в интернете при длительном поиске.

Если поиск продолжается более 30 минут, сервер должен автоматически запускать дополнительную задачу ИИ-агента без дополнительной оплаты.

Ответы ИИ необходимо обрабатывать и проверять на корректность структуры, а также отделять предположения от подтверждённых аптекой сведений.

## 8. База данных

Рекомендуемая основа — PostgreSQL с возможностью использования PostGIS для географического поиска.

Предусмотреть таблицы или соответствующие модели данных для:
- Пользователей.
- Сессий.
- Поисковых заказов.
- Препаратов.
- Единого каталога лекарств.
- Аптек.
- Торговых точек.
- Интеграций.
- Ответов аптек.
- Платежей.
- Чатов.
- Сообщений.
- Истории заказов.
- Чёрного списка препаратов.

Все изменения структуры базы данных должны оформляться миграциями.

Технологию очередей для долгих поисковых операций и фоновых задач выбрать отдельно.

## 9. Система тестирования

Тесты должны разрабатываться одновременно с основным кодом.

Недостаточно просто проверить приложение вручную перед релизом.

Необходимо создать автоматизированную систему тестирования, которая запускается при каждом изменении проекта.

### 9.1. Flutter

Обязательные тесты:

**Unit-тесты:**
- Проверка формирования поискового запроса.
- Проверка количества и характеристик препаратов.
- Проверка обработки ответов аптек.
- Проверка статусов оплаты.
- Проверка сортировки результатов.
- Проверка перевода чатов в архив.

**Widget-тесты:**
- Экран регистрации.
- Экран создания поиска.
- Экран оплаты.
- Экран результатов.
- Экран чата.

**Интеграционные тесты:**
- Полная регистрация пользователя.
- Создание поискового запроса.
- Получение предварительного результата.
- Успешная оплата через тестовый провайдер.
- Получение результатов.
- Общение с аптекой.
- Архивирование чатов.

Отдельно проверить работу геолокации и OCR на тестовых устройствах.

### 9.2. Rust Backend

Обязательные тесты:

**Unit-тесты:**
- Сопоставление препаратов.
- Определение полного и частичного совпадения.
- Расчёт стоимости.
- Поиск аптек по координатам.
- Расширение радиуса поиска.
- Ограничение частоты запросов.
- Обработка ответов аптек.
- Обработка платежей.
- Проверка срока действия чатов.

**Integration-тесты:**
- Работа API.
- Взаимодействие с базой данных.
- Создание поискового заказа.
- Получение результатов аптек.
- Проверка платёжных уведомлений.
- Проверка интеграционных адаптеров.

**Нагрузочные тесты:**
- Одновременная обработка нескольких поисков.
- Большое количество подключённых аптек.
- Получение большого количества ответов.
- Параллельное выполнение фоновых задач.

Для внешних сервисов использовать тестовые заглушки (Mock): это позволит запускать тесты без реального банка, аптек и ИИ-провайдера.

### 9.3. Автоматический запуск тестов

Настроить CI/CD.

При каждом изменении кода автоматически запускать:
1. Проверку форматирования.
2. Статический анализ.
3. Unit-тесты.
4. Integration-тесты.
5. Сборку приложения и сервера.

Не допускать автоматического попадания изменений в основную ветку, если обязательные проверки завершились ошибкой.

Для критической бизнес-логики рекомендуется установить минимальное покрытие тестами 80%.

## 10. Debug Log и мониторинг

В приложении и сервере должна быть полноценная система логирования.

Цель — иметь возможность понять, что происходило во время ошибки, где она возникла и почему.

### 10.1. Логи мобильного приложения

В режиме разработки приложение должно записывать:
- События авторизации.
- Создание поисковых запросов.
- Запросы к серверу.
- Ответы сервера.
- Ошибки сети.
- Ошибки геолокации.
- Ошибки OCR.
- Ошибки оплаты.
- Ошибки отображения результатов.

Для каждого события указывать время и уровень важности.

### 10.2. Серверные логи

Сервер должен записывать:
- Входящие API-запросы.
- Время обработки запросов.
- Создание поисковых задач.
- Обращения к аптекам.
- Ответы аптечных систем.
- Ошибки интеграции с 1С.
- События платёжной системы.
- Работу ИИ-агентов.
- Ошибки базы данных.
- Ошибки фоновых задач.
- Изменения статусов поисковых заказов.

Каждый лог должен содержать идентификатор запроса (request_id), а поисковые события дополнительно — search_id.

Это позволит восстановить полную последовательность событий одного поиска.

### 10.3. Уровни логирования

Использовать стандартные уровни:

- DEBUG — подробная информация для разработки.
- INFO — обычные события системы.
- WARN — потенциальные проблемы.
- ERROR — ошибки, требующие внимания.

В production DEBUG должен быть отключён по умолчанию и включаться только контролируемым способом.

### 10.4. Безопасность логов

Запрещено записывать в логи:
- Коды подтверждения.
- Пароли и токены авторизации.
- Платёжные секреты.
- Полные платёжные данные.
- Фотографии рецептов.
- Необработанные персональные данные.
- Полные сообщения с чувствительной информацией о здоровье.

Для диагностики использовать внутренние идентификаторы пользователей и заказов вместо номеров телефонов.

### 10.5. Формат и хранение

Предпочтительный формат — структурированные JSON-логи.

Предусмотреть возможность:
- Фильтрации по search_id.
- Фильтрации по пользователю.
- Поиска ошибок по времени.
- Просмотра истории конкретного запроса.
- Определения наиболее частых ошибок.

Срок хранения логов и способ их просмотра необходимо определить при развёртывании.

## 13. Критерии готовности MVP

Проект считается готовым к тестированию, когда:

- Пользователь может зарегистрироваться.
- Может создать запрос с несколькими препаратами.
- Может выполнить предварительную проверку.
- Может оплатить поиск в тестовом режиме.
- Сервер способен обработать поисковый запрос.
- Работает получение ответов от тестовых аптек.
- Реализовано разделение полных и частичных совпадений.
- Результаты отображаются в приложении.
- Пользователь может открыть чат и связаться с аптекой.
- Работает архивирование чатов.
- Ведётся история поисков.
- Автоматические тесты проходят успешно.
- Ошибки приложения и сервера фиксируются в логах.

Реальные банковские и аптечные интеграции допускается подключать по мере получения доступов и технической документации от партнёров.
